Entitlements answer the two questions your app asks constantly: *can this
customer use this feature?* and *what is their limit?*

## Checking access

```python
with billing.transaction() as services:
    allowed = services.entitlements.can(customer.id, "reports")
    seats = services.entitlements.limit(customer.id, "seats")
    value = services.entitlements.value(customer.id, "api_calls")
```

| Method | Returns |
|---|---|
| `can(customer_id, feature_key)` | `bool` — effective value/limit is greater than zero |
| `limit(customer_id, feature_key)` | `int \| None` — explicit `limit_value`, else the value for non-boolean features, else `None` |
| `value(customer_id, feature_key)` | `int` — the effective numeric value |
| `resolve(customer_id, feature_key)` | A `ResolvedEntitlement` with full detail |
| `list_for_customer(customer_id)` | `{feature_key: ResolvedEntitlement}` for every known feature |

```python
resolved = services.entitlements.resolve(customer.id, "seats")
print(resolved.source)      # customer | subscription | plan | default
print(resolved.value, resolved.limit_value)
```

## Resolution order

The engine walks this chain and returns the first match:

1. **Customer override** — applies to the customer regardless of subscription.
2. **Subscription override** — applies to the customer's active subscription.
3. **Plan entitlement** — from the current plan version.
4. **Feature default** — the feature's `default_value`.

Expired overrides are skipped. The **active subscription** is the one that
`grants_access` (status `trialing`, `active`, or `past_due`), preferring the one
with the latest `current_period_end`.

:::note[Caching]
Resolution is computed on demand. Treat a transaction as the freshness
boundary: read entitlement decisions inside the same request that reads the
data they guard.
:::

## Overrides

Overrides let you grant, raise, or lower a feature without touching the plan.
They are stored per customer or per subscription and can expire automatically.

<Tabs>
  <TabItem label="Customer override">
```python
services.entitlements.set_customer_override(
    customer.id,
    "seats",
    value=1,
    limit_value=25,
    reason="annual deal",
)
```
  </TabItem>
  <TabItem label="Subscription override">
```python
services.entitlements.set_subscription_override(
    subscription.id,
    "reports",
    value=1,
    expires_at=datetime(2026, 12, 31, tzinfo=UTC),
    reason="temporary access",
)
```
  </TabItem>
</Tabs>

### Precedence example

If a customer override and a subscription override both exist, the **customer**
override wins. Remove it to fall back to the subscription override:

```python
override = services.entitlements.set_customer_override(customer.id, "seats", limit_value=3)
services.entitlements.set_subscription_override(subscription.id, "seats", limit_value=9)

services.entitlements.limit(customer.id, "seats")          # 3 (customer wins)
services.entitlements.remove_override(override.id)
services.entitlements.limit(customer.id, "seats")          # 9 (subscription now applies)
```

Setting an override with the same scope and feature **replaces** the previous
one; each change is audited with a reason.

## Worked example

Plan grants `seats` with `value=1, limit_value=5`. A customer override sets
`limit_value=25` but expires yesterday. Resolution ignores the expired override
and falls back to the plan:

```python
services.entitlements.set_customer_override(
    customer.id, "seats", limit_value=25, expires_at=utcnow() - timedelta(days=1)
)
services.entitlements.limit(customer.id, "seats")   # 5 — override is expired
```

## Errors

| Situation | Error |
|---|---|
| Unknown `feature_key` | `NotFoundError` |
| Unknown customer/subscription when writing an override | `NotFoundError` |
| Empty `override_id` on remove | `ValidationError` |
